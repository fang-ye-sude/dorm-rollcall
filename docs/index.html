宿舍点名 · 项目手册

B 座住宿生 点名 → 三表 应用容器 一体机

钱七在 iPad 点完名、上传，系统把请假四维写进三张共享表；周日晚自动发下周新表，周五自动备份。

一、概览 谁在用、在哪、什么时候跑

宿管老师
iPad「B座点名」：逐房点缺勤，选 DS/DB/XS/XB，上传。
家长
钉钉共享链接看请假汇总、周末返校、体温三张表。
管理者
网页控制台：发布、查看、试运行、手动填、切表。
系统
应用容器 定时器：发布、填表、补扫、月表、备份。

二、每日流程 一晚只需三步

① 点名钱七逐房点缺勤，标四维；周日返校记得勾"周末统计"。
② 上传点「上传标记件」。想立刻出表就点「立刻填表」，不点等 21:40。
③ 看一线控制台三格全绿：件到了、计划处理了、三表写了。

控制台怎么看

  • 今日一线：① 点名件（时间/人数/含不含返校）② 待填计划（几份）③ 写入三表（今日是否已写、最近销账时间）。
  • 有计划时，卡片上直接出「试运行」与「写入三表并销账」两颗钮。
  • 待填计划里写着"将写：主表第 N 行 · 体温 M 月 D 日 X 格"，名单可展开核对。
  • 底下「最近记录」是最近几次入箱与销账，肉眼可查今晚是否真写过。
三步只需看三处：一线是否绿、最近记录有没有"销账 当日"、任务输出有没有红字。

三、周表发布 周日自动，也能手动

自动：周日 07:30 取下一个周日的日期区间，用标版生成两张 xlsx → 转在线表 → 加群权限 → 发链接 → 旧表撤权改名"已撤-" → 回写配置。

手动发布

  1. 「发布周表」选日期，或点 本周 / 下周 / 上周（自动落周日）。
  2. 看徽章：11.08~11.12（周日–周四）。
  3. 看提示：
    • 正常：「将生成 11.08~11.12 两表；将撤下 11.01-11.05…」
    • 红字：「⚠️ 该周已在役，再发布将撤权旧表并重建」——多半是误点，停手核对。
  4. 点「生成并发布」，按钮变"发布中…"，完成后看任务输出。
重复发同一周，等于把自己正在用的表撤掉再建。新表是空表，此前几天填过的数据不会带过去。

四、填表 从件到三表

上传件落 data/marked/，一体机算计划放 data/pending/<date>.json；pipeline_ops fill 取计划写表，成功后 ack 销账。

步做什么失败了会怎样
取件读当日计划空箱且今日无件 → 静默
自检日期／块号／行位是否自洽报错不写，留信箱等处理
写主表C..L 十格 + 名单任一失败整份不销账
写周末表仅勾了返校的件同上
写体温本地 xlsx 当日列 + 在线同步缺人跳过记日志，不阻断
销账计划移入 logs/done/未销账 → 23:50 补扫重试

三种触发

  • 定时：21:40 自动；23:50 补扫只处理空箱。
  • iPad：「立刻填表」→ 一体机 /write-now → 跑同一套流水线（单飞，连点只跑一次）。
  • 控制台：「试运行」先空跑看日志；「写入三表并销账」一次落定。
写表前会比对"回读值"，不一致不销账——所以表上数字与点名件必然对得上，对不上就是没写成功。

五、三张表 结构与写入位

九、工作原理 件、计划、表；为什么能自己跑对

件（事实）iPad 点完的原始记录，只增不改，永久留档。
计划（意图）由件算出"该日该块要写的十格"，一天一份。
表（结果）家长看到的三张表，是计划的投影，可重写。

状态机

上传 → 入信箱 → 自检 → 写主表 → 写周末 → 写体温 → 回读校验 → 销账
                     │                                        │
                     └─ 不自洽：不写（宁可不动，不乱写）        └─ 失败：留信箱，23:50 重试

四条不变量：不销账等于没成；写前自检日期/块号/行号；写后回读逐格比对；只补体温不写主表时不销账。

日期与块

周日到周四对应块 0~4，数据行 15/39/63/87/111。调休由 config.blockmap 显式指定块号；跨月按计划日期选 sheet，不看运行时刻。

为什么要写成 SUM

原表用加法公式，一碰文字占位 - 就 #VALUE! 并顺着引用传染。全表改 SUM(...)：忽略非数字，正好等于"占位符不算数"。

三个入口，一把锁

定时、补扫、手动可能同时触发。文件锁 + 接口单飞 + 原子写三层挡住重复写与半截 JSON。写表幂等，所以失败重跑安全。

失败恢复

断在哪怎么补
上传前断网数据在 iPad 本地，联网重传
上传后未填控制台点「写入三表并销账」
写体温失败单跑 fill --targets=temp，再销账
发布失败重跑发布；旧表在成功后才撤权
详见 07-工作原理.md：状态机、并发、缓存、鉴权、时序列全在里面。

十一、全楼扩展 男三层 + 女四层（2–5）

一台 应用容器 扛七层。按楼栋拆表、按层分块；名册、件、计划、表全部带 building 维度，同房号跨栋不混。

A1 归一化别名 + 同房内模糊匹配，姓同且编辑距离 ≤1 才建议，不越栋认错。
A4 冲突消解操作日志 + 幂等键 + 时间戳后写赢，五点内四维不一致进人工复核。
A5 离线同步本地队列、幂等去重、先传后拉；断网照点，恢复自动补传。
面做法
网络校内直连 应用容器，跨楼走公网隧道；断网排队，弱网指数退避
客户端楼栋→楼层→房间→名单；大字号、四维四色、整层套用、语音播报可选
权限点位 token 按层发；管理员全改、层管本层、家长只看表
智能规则做异常，模型只写日报与答话，不写表、不碰人脸
上线B 座三层 → 女生楼 2–5 层 → 全校汇总与告警
算法伪代码、容量估算、参考项目与衔接清单见 08-全楼推广设计.md。

十二、账户与点位 每层一台 iPad，各登各的账号

三个问题分开认：认人（账号）、认层（scope）、认机（点位）。核心一句：楼栋与楼层由服务端按账号决定，客户端说了不算。

角色能做不能
floor 层管点名、标四维、上传、立刻填表、看本层别层名册与表
admin 管理员全部、切层、发周表、建账号、挂失点位—
viewer 只读看本层表与当日件上传

登录与令牌

账号+密码 → /auth/login → access_token(2h) + refresh_token(90天，绑设备指纹)
iPad：access 内存，refresh 进 Keychain；过期自动换

断网时凭本地缓存名册与签名短令牌继续点名，操作进队列，恢复按序补传。

上传路由

POST /upload  Bearer <token>
→ 验签得账号与 scope
→ building/floor 取账号的，body 里的楼栋字段一律忽略
→ 不在本层的人记"越层名单"，不进计划

换机与挂失

点位挂失即废 refresh_token，新 iPad 重登生成新点位；名册与历史不受影响。

账号模型、接口草案、迁移步骤见 09-账户与点位.md。

十三、线上更新 打开 App 点一下就更

先分清：表格在云端不下载；要更新的只有名册与页面代码。名册按账号 scope 下发本层，代码整包校验后原子切换。

启动 → 请求 manifest（app_version / roster_version / 文件哈希）
有更新 → 点「更新」→ 下载变动文件到暂存区 → sha256 校验
全部通过 → 原子切换并保留旧版 → WebView 重载
任一失败 → 删暂存区，继续用旧版
规矩说明
先下后切不边下边用，校验不过不切换
数据不丢未上传的标记与队列独立存放，更新不动
可回滚保留上一版，起不来一键退回
可灰度先只给 B 座一层发新版，稳两天再全量
断网不扰检查失败静默用本地版，点名不依赖更新成功
目录结构、接口、发布命令与安全细则见 10-线上更新.md。
