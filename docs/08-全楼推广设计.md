# 08 · 全楼推广设计（男三层 · 女四层）

> 面向 SSDM-2026 的扩展稿：从 B 座一层 → 男生三层（1–3）+ 女生四层（2–5），共七层。
> 2026-11-03 起草。分"大纲、架构、算法、网络、客户端、智能、上线"七段。

## 一、大纲

### 目标

1. 一套系统覆盖男 3 层 + 女 4 层，七层各自点名、各自出表，楼栋与全校自动汇总。
2. 每层至少一台 iPad，多机同时点名互不冲突；断网不丢数据。
3. 老师只管自己那层，管理员看全校，家长按楼栋/周看表。
4. 复用现有"件—计划—表"产线，新增"楼栋/楼层"维度，不改学校表格式。

### 范围

- **在范围**：多层点名、三表多栋、楼层汇总、异常告警、权限分层、离线同步。
- **不在范围**：门禁硬件改造、学生自助请假审批（可后续）、人脸采集（仅列为可选）。

### 节奏

```
阶段 0  现状：B 座一层单机（已稳定）
阶段 1  B 座三层：同机扩展，多表多点位（1–2 周）
阶段 2  女生楼四层（2–5 层）：加楼栋维度（2–3 周）
阶段 3  汇总与告警：全校视图、异常名单、日报（持续）
```

要点：**一台 应用容器 扛七层**。人数约 7 层 × 20 房 × 8 人 ≈ 1100 人，一晚一件一栋，写入量可控；瓶颈在钉钉表格 API，因此按楼栋拆表、按周拆表，避免单表过大。

## 三、数据模型

```
Building { code, name, floors[], tables { main, weekend, temp } }
Floor    { building, no, points[] }        # 点位 = iPad
Room     { building, floor, room, students[] }
Student  { name, class, building, floor, room, aliases[] }
Point    { id, name, building, floor, device, owner, last_seen }
Event    { date, building, floor, point, names[], weekend }
Plan     { date, building, block, row, values[], students[], marked_file }
```

关键：所有记录都带 `building` 与 `floor`，**日期 + 楼栋 + 点位** 决定唯一性。名册升级为多栋：同一房号在不同楼栋必须靠 `building+room` 区分，不能只认房号。

## 四、算法细节

### A1. 名字与房的归一化（最易错，先固）

```
输入：点名件里的 [name, room, q]
1. room 规范化：去空格、全角转半角、房号补齐（如 "3" → "103" 按楼层推断）
2. name 规范化：去班级后缀（"学生79 网络" → 学生79）、去 NBSP、去空格
3. 查别名表（name_aliases）
4. 若无别名，在同 (building, room) 内做模糊匹配：
   - 同音字 / 形近字（杨箫↔学生286、邹李沐岐↔学生450）
   - 编辑距离 ≤ 1 且姓相同 → 候选，写入"疑似别名"待人工确认
5. 仍无 → 记"缺人跳过"，并列入当日异常清单
```

为什么不用全楼模糊匹配：同房才比，避免把"张伟"错认成另一栋的张伟。

### A2. 楼层 → 表行映射

```
每栋每周一张主表；表内按层分块（男三层：块=层）
block = f(楼层)            # 楼栋内
row   = head(block) + 14   # 与现行一致
日期  → 周几决定"第几天"
```

扩展：女生楼四层，仍用同一模板（块数可变），按楼栋发表。调休沿用 `config.blockmap`，但改为 `blockmap[date][building]`。

### A3. 点名件 → 计划（幂等）

```
key = (date, building)                     # 一栋一天一份
若同日多件：按 mtime 取最新；旧件直接归档
plan.values = 按四维聚合（DS/DB/XS/XB）
plan.students = 缺勤逐人，含房号与班级
```

同一层两台 iPad 同时点：以**楼栋 + 日期**合并，而不是互相覆盖——见 A4。

### A4. 多点位冲突消解（本方案的核心）

场景：两台 iPad 点同一层，A 机标"张三 DS"，B 机标"张三 XS"。

算法：**操作日志 + 幂等键 + 后写赢 + 人工复核**

```
每个标记是一条 op: {student, q, ts, point, op_id}
op_id = hash(student + q + point + ts)     # 幂等，重传不产生新 op
按 ts 升序合并；同 student 取 ts 最新
若两点在 5 分钟内标了不同四维 → 标记 conflict，写入表时以最新值落，
  并在控制台生成"冲突待复核"条目，由层管一键裁定
```

为什么不用简单覆盖：A 机离线一小时后补传，不能把 B 机刚标的新值盖掉；时间戳 + 冲突提示比"谁后传谁赢"更稳。

### A5. 离线同步（网络不稳时的保底）

```
iPad 本地：SQLite（或 localStorage 简化）存 op 队列 + 当前名册快照
联网时：按 op 顺序补传（带 op_id），服务端幂等去重
断网时：继续点，UI 显示"待同步 N 条"
恢复：先传后拉，冲突走 A4
```

网络层：优先校内 LAN/热点直连 应用容器；不通时走公网隧道；两处皆断则排队，不弹错不丢数据。

### A6. 体温与异常

- 在校生的体温仍由公式生成（36.3–37.0）；请假者写"事/病"。
- 异常规则：
  - 体温 ≥ 37.3 → 标红 + 当日名单；
  - 连续 3 日病假 → 列入"需回访"名单；
  - 同一房一晚 ≥ 3 人请假 → 预警（疑似集中事件）。
- 这些都是**规则 + 阈值**，不引入模型；结果写入当日"异常清单"，随日报发群。

### A7. 汇总算法

```
每层：应到 = 该层名册数；实到 = 应到 − 请假；请假率 = 请假 / 应到
楼栋：Σ 各层；全校：Σ 各栋
日趋势：近 14 天按楼栋滑动平均；突增（> 均值 + 2σ）→ 标黄
```

输出三处：控制台全校卡、每周汇总表、群里一条摘要。

### A8. 写入与重试

沿用现行铁律并扩展：

1. 按楼栋分计划，互不影响；一栋失败不拖另一栋。
2. 每栋内部仍有自检 → 写入 → 回读 → 销账。
3. 失败进该栋信箱，23:50 按栋补扫。
4. 全程幂等：重跑不产生新行，重复销账视为已完成。

## 五、网络方案

| 场景 | 做法 |
| --- | --- |
| 校内同网 | iPad 直连 应用容器:8100（内网），延迟最低 |
| 跨楼宇/校外 | 经 `example.com/dianming/api/`（北京轻量 → WG → 应用容器） |
| 断网 | 本地队列，恢复自动补传 |
| 弱网 | 请求带超时与重试（指数退避 1s/2s/4s），不传大文件 |
| 安全 | 全链路 TLS；token 按点位分发；日志不落 token |

容量估算：1100 人、每晚 7 件、每件 ≤ 20KB，日产出不足 1MB；五年留档约 2GB，现有盘足够。

## 六、客户端重做（iPad）

### 结构

```
楼栋 → 楼层 → 房间 → 名单（四维）
```

- 顶部固定：楼栋 / 楼层 / 日期 / 同步状态（绿点 + "待同步 N"）。
- 房间横滑切换；学生卡片大字号，四维四色（DS 蓝、DB 红、XS 橙、XB 紫）。
- 支持"整层复制"：同一原因批量套用到同房多人。
- 缺勤列表实时汇总在底部抽屉，点人可改四维。
- 语音播报（可选）："103 房 2 人请假"。

### 账号与点位

- 每台 iPad 绑定点位（楼栋 + 楼层），登录即定位，不用每次选。
- 教师只看到自己那层；管理员可切层。

### 上传与确认

- 上传后明确提示："已上传 13 人 · 点此写入共享表"，避免不知道发生了什么。
- 「立刻填表」返回结果直接显示："主表行 39 已写 · 体温 13 格 · 已销账"。

### 多端

- 同一层可多台；冲突由 A4 处理。
- 提供网页版入口给管理员手机（只读查看 + 审批冲突）。

## 七、人工智能用在哪（务实版）

| 用点 | 做什么 | 是否必须 |
| --- | --- | --- |
| 异常检测 | 连续病假、集中请假、体温越界（A6，规则即可） | 推荐 |
| 日报生成 | 把当日各层数据写成一段人话发群 | 推荐 |
| 自然语言查数 | "上周三 103 谁请假" → 转查询 | 可选 |
| 名字纠错 | 形近字/同音字建议（A1 规则已够，模型仅作建议） | 可选 |
| 人脸识别 | 门禁归寝自动点名 | **不做默认**，涉隐私，需单独审批 |

原则：**能规则解决的别上模型**；模型只做"写人话、答人话、提建议"，不参与写表。

## 八、安全与权限

- 点位 token 按层发放，泄露只影响该层；可单独吊销。
- 管理员 / 层管 / 家长三级：管理员全改，层管只读本层与标记，家长只看表。
- 名册、体温、请假记录按"必要可知"分发；共享表按楼栋分，不混全校。
- 审计：每次写表记"谁、哪台、几点、写了几格"，保存一年。

## 十一、与现系统怎么接

1. 现有 `data/marked`、`pending`、`logs` 结构加 `building` 字段，老数据默认 `building=B`。
2. 现控制台「今日一线」加楼栋切换；默认显示 B 座。
3. 现体温主档按楼栋分文件；旧 `宿舍点体温.xlsx` 自动归入 B 座。
4. 现发布/填表命令加 `--building` 参数，默认 B，老定时任务不用改。
5. 客户端老版本仍能上传（视作 B 座一层），新版本再逐步换机。

## 十二、不做的事（防止摊子铺太大）

- 不做门禁、不做闸机、不做人脸库。
- 不做学生自助请假审批流（那是另一套系统）。
- 不做跨校区、不做多租户 SaaS。
- 不在客户端装 AI 模型；智能能力全放服务端。
