# 10 · 线上更新（打开 App 点一下就更）

> 目标：名册变了、页面改了、模板换了，老师打开 App 点「检查更新」，一次到位，不重装。
> 2026-11-03 起草。配套 `09-账户与点位.md`。

## 一、先分清三种"更新"

| 东西 | 在哪 | 要不要下载到 iPad |
| --- | --- | --- |
| 名册（谁住哪房、哪个班） | 应用容器 `roster_b1f.json` | **要**（按账号 scope 下发本层） |
| 页面代码（index.html 及逻辑） | 应用容器 静态目录 | **要**（打包下发） |
| 表格（请假汇总/周末/体温） | 钉钉在线表 | **不要**（表在云端，客户端只写不存） |

所以"大表改了"若指名册/房型，走的是名册更新；若指学校那张共享表，客户端根本不用更新——它每晚自动写新表。

## 二、清单（manifest）

服务端只出一个入口：

```json
{
  "app_version": "1.2.0",
  "roster_version": 20261103,
  "min_supported": "1.1.0",
  "scope": {"building": "B", "floor": 1},
  "files": [
    {"path": "index.html", "sha256": "…", "size": 182344, "required": true},
    {"path": "roster.json", "sha256": "…", "size": 20480, "required": true}
  ]
}
```

- `app_version`：页面代码版本；`roster_version`：名册版本。
- `files`：本次要更新的文件与哈希；客户端逐个比对，只下载变了的。
- `required`：为 true 的文件失败则整体不切换（防半新半旧）。
- `scope`：按登录账号返回本层清单，别层名册不下发。

## 三、客户端流程

```
启动 → 读本地版本 → 后台请求 manifest
  ├ 版本一致 → 静默，不打扰
  └ 有更新 → 顶部出现「有更新 · 点击更新」

点更新 →
  1. 下载变动文件到「更新暂存区」
  2. 逐个 sha256 校验，大小也要对
  3. 全部通过 → 原子切换（旧版整体改名备份，新版换上）
  4. 弹窗「更新已完成」：立即重启 / 稍后重启
     - 立即重启 → 客户端重新加载新包
     - 稍后重启 → 继续用当前页，下次启动自动走新包
  任一步失败 → 删暂存区，继续用旧版，提示"稍后再试"
```

三条铁律：

1. **先下载后切换**，绝不边下边用。
2. **校验不过不切换**，失败不影响现有版本。
3. **点名数据不丢**：本地未上传的标记与队列独立存放，更新不动它们。

## 四、服务端目录

```
/srv/dormroll/app/web/            # 当前发布的页面包
  index.html
  manifest.json                   # 由发布脚本生成
/srv/dormroll/app/releases/       # 历史版本（保留最近 5 个，便于回滚）
  1.1.0/  1.2.0/
```

发布命令（脚本化）：

```bash
python3 ops/client_release.py --version 1.2.0 --dir ./web-dist
# 复制到 releases/1.2.0，生成 manifest（含 hash），切换 app/web 软链
```

名册不必走发布：`roster_b1f.json` 改完，服务端自动 bump `roster_version`。

## 五、接口

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/manifest` | 按 token scope 返回清单（版本、文件哈希） |
| GET | `/static/client/<path>` | 下载页面文件（带 hash 校验） |
| GET | `/api/roster` | 下载本层名册（带 roster_version） |
| GET | `/api/roster/version` | 只查名册版本，省流量 |

`manifest` 与 `roster` 需要登录；静态包可公开但不含学生信息。

## 六、回滚与灰度

- 本地始终保留上一版完整副本；新版起不来时一键"回到旧版"。
- 灰度：先只对 B 座一层账号下发新版本，其余楼层 manifest 仍指旧版；稳定两天再全量。
- 强制升级：`min_supported` 低于当前客户端版本时，App 提示"请先更新"，但仍允许先看完本地数据再更新，不拦路。

## 七、断网与弱网

- 启动检查失败 → 静默用本地版，不弹错。
- 下载中断 → 已下文件保留在暂存区，下次从断点续传（按文件粒度）。
- 全部依赖只在有网时检查；点名功能本身不依赖更新成功。

## 八、安全

- 全部走 HTTPS；名册按 scope 下发，别层账号拿不到别层名单。
- 文件哈希必校验；`manifest` 可选再签一层 HMAC，防中间人换包。
- 更新日志记账号、点位、版本、结果，便于追查"哪台没更新"。

## 九、老客户端怎么获得更新能力

现在这版（1.1）没有更新器，需要**最后一次手动装**：

1. 装一次带更新器的新壳（TestFlight 或直接安装）。
2. 此后所有名册、页面、逻辑更新都走线上，不再重装。

## 十、与账号系统的关系

- 更新清单按账号 scope 生成：二层账号只拿到二层名册与对应页面。
- 管理员可强制某层先更新做试点；普通层管只看到自己那层的"有更新"。
- 账号被吊销后，更新请求一并 401，不会再拿到新名册。

## 十一、实施记录（2026-11-03）

已落地并验证：

| 层 | 实现 | 位置 |
| --- | --- | --- |
| 清单 | `GET /api/manifest`（版本 + 名册版本 + 文件 sha256/size + scope/label） | 应用容器 `rollcall_suite.py` |
| 下载 | `GET /static/client/<path>`（realpath 防穿越） | 同上 |
| 名册 | `GET /api/roster`、`/api/roster/version` | 同上 |
| 发布 | `client_release.py --version X --dir DIR`：复制 → 生成 manifest → 原子切 `app/web` 软链 → 留 5 版 | `ops/client_release.py` |
| 原生 | `otaBridge`：下载 → CryptoKit 校验 → `web-next` → 原子换 `web` → 弹窗待重启；`restart` 重载、`rollback` 回滚 | `DormRoll/main.swift` |
| 页面 | 启动 1.5s 后自动检查，有更新出浮动按钮，点即更新 | `DormRoll/index.html` |
| 加载 | 优先 `Documents/web/index.html`，没有再回 bundle | 同上 |

实测：`/api/manifest` 返回 1.2.0 → 下载 `/static/client/index.html` 与 sha256 完全一致 → 发布 1.2.1 → 清单即刻变 1.2.1。客户端已编译签名并装到学生211 iPad（bundleID `com.example.dormroll`）。

2026-11-03 追加：下载完成后改为**弹窗询问**「立即重启 / 稍后重启」，立即重启才重新加载客户端；当前线上 1.2.3，iPad 端 1.2.2。

**使用**：老师打开 App，若出现"有更新 · 点击更新"，点一下即可；失败自动留旧版。

## 十二、一句话

**表格在云端不动，名册按层下发，代码整包校验后原子切换。** 老师只需点一下"更新"，名册与页面一起换新；不成还能退回旧版，点名数据一根汗毛都不动。
