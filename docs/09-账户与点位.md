# 09 · 账户与点位（每层一台 iPad）

> 目的：每层一台 iPad，登录谁的账号，就只看见谁那层的名单；上传自然落到那层，改不了。
> 2026-11-03 起草。配套 `08-全楼推广设计.md`。

## 一、先把问题拆开

"不同账号显示不同表、发到对应楼层"，其实是三个独立问题：

1. **认人**：谁在用这台 iPad（账号）。
2. **认层**：这个账号管哪栋楼哪一层（scope）。
3. **认机**：这台设备是不是登记过的那台（点位）。

关键是：**楼栋与楼层由服务端根据账号决定，客户端说了不算**。iPad 只传"谁、什么假"，不传"这是哪层"——传了也不认。这样即使有人改包、改参数，也写不进别人的楼层。

## 二、账号模型

```json
{
  "id": "f1-b2",
  "name": "B座二层·学生211",
  "role": "floor",                  // floor=层管 / admin=管理员 / viewer=只读
  "scope": {"building": "B", "floor": 2},
  "pass_hash": "pbkdf2$…",
  "must_change_password": false,
  "point_ids": ["ipad-b2-01"],
  "enabled": true,
  "created": "2026-11-03"
}
```

| 角色 | 能做什么 | 看不到什么 |
| --- | --- | --- |
| floor | 点名、标四维、上传、立刻填表、看本层历史 | 别层名册与表 |
| admin | 全部楼层、切层、发周表、建账号、吊销点位 | 无限制 |
| viewer | 只读自己那层表与当日件 | 不能上传 |

一个账号**只绑一个 scope**；管理员是特殊账号，scope 为 `*`，可在客户端切层，但切层动作本身要记日志。

## 三、登录与令牌

不引 OAuth，学校里用不上那么重。流程：

```
账号 + 密码  →  /auth/login  →  返回：
  access_token（短期，2 小时）
  refresh_token（长期，90 天，绑设备指纹）
  scope {building, floor}
  roster_version

iPad 保存：access_token 内存、refresh_token 进 Keychain
之后每次请求带 access_token；过期用 refresh_token 换新的
```

设备指纹 = 首次登录时客户端生成的随机 `device_id`（UUID），连同设备名一起登记成点位。refresh_token 与 `device_id` 绑定，换机或刷机后必须重新登录——丢了一台 iPad，只废掉那一台的令牌。

### 断网怎么办

access_token 用**签名短令牌**（HMAC），内容含账号、scope、过期时间；iPad 本地能离线验签与过期判断。断网时：

- 仍可打开本层名册（已缓存快照）；
- 仍可标四维，写入本地队列；
- 上传按钮显示"待同步 N 条"，恢复后按序补传。

服务端不信任离线结果的时间戳以外的任何"我已登录"声明；真正写表仍以服务端验签为准。

## 四、服务端路由（核心）

```
POST /upload
  Authorization: Bearer <access_token>
  body: { date, weekend, n:[[name, room, q], …] }

服务端：
 1. 验签 → 得 account 与 scope
 2. scope 为 floor：building/floor 取账号的，忽略 body 里任何 building 字段
 3. 名册以该 scope 过滤，凡不在本层的人 → 记"越层名单"，不入计划
 4. 生成件：data/marked/<building>/<date>-<point>.json.gz
 5. 计划：data/pending/<building>/<date>.json
```

**越层名单**要显式提醒：本层老师若误点了别层的人，控制台能看到"有 2 人不在本层，已忽略"，防止悄悄漏人。

### 名册下发

```
GET /api/roster            → 按 token scope 返回该层名单（含房、班、别名）
GET /api/roster/version    → 返回 roster_version
```

客户端启动比对版本号，不同才重拉；名册变更在服务端改 `roster_b1f.json` 并 bump 版本。这样七台 iPad 不会天天全量拉名单。

## 五、客户端（iPad）流程

### 首次

1. 打开 App → 登录页（账号、密码）。
2. 登录成功 → 自动定位"楼栋 / 楼层"，下载该层名册。
3. 直接落到房间列表，老师无感。

### 日常

- 顶部固定："B座 二层 · 学生211" + 同步状态。
- 无楼栋/楼层选择器（层管不需要），管理员才有切层入口。
- 上传成功回："B座二层 · 13 人已上传"。
- 立刻填表回："主表第 39 行 · 体温 13 格 · 已销账"。

### 换机 / 丢机

- 管理员在控制台把该点位标记"挂失"，refresh_token 即刻失效；
- 新 iPad 重新登录即生成新点位，旧点位进历史；
- 挂失不影响账号本身，名册与历史仍在。

### 退出登录

只清本机令牌与缓存名册，不影响服务端已上传的数据。

## 六、安全细则

| 项 | 做法 |
| --- | --- |
| 密码存储 | PBKDF2-HMAC-SHA256，20 万次迭代，盐随机；不存明文 |
| 初始密码 | 管理员生成一次性初始密码，首次登录强制改密 |
| 登录限流 | 同账号 5 次失败锁 10 分钟；同 IP 失败 20 次锁 30 分钟 |
| 令牌 | access 2 小时、refresh 90 天；refresh 可单独吊销 |
| 传输 | 全 TLS；token 只走 Authorization 头，不进 URL、不进日志 |
| 审计 | 登录、上传、切层、挂失、改密，全部记时间+账号+点位 |
| 越权 | 任何 building/floor 以账号 scope 为准，客户端参数一律忽略 |

## 七、接口草案

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| POST | `/auth/login` | 账号密码换双令牌 + scope + roster_version |
| POST | `/auth/refresh` | 用 refresh_token 换新 access_token |
| POST | `/auth/logout` | 吊销本机 refresh_token |
| GET | `/api/roster` | 按 scope 取本层名册 |
| GET | `/api/roster/version` | 名册版本号 |
| POST | `/upload` | 上传件（scope 由 token 决定） |
| POST | `/write-now` | 立刻填表（同上） |
| GET | `/api/pending` | 按 scope 取本层计划 |
| POST | `/api/ack` | 销账（按 scope 限定） |
| GET | `/api/history` | 按 scope 取本层历史 |
| admin | `/admin/accounts` `/admin/points` | 建账号、改 scope、挂失、吊销 |

旧 `?token=` 与 `?admin=` 保留兼容：旧 token 视作 B 座一层账号，旧 admin 视作管理员。老客户端不用急换。

## 八、最小数据文件

```
data/state/accounts.json     # 账号与 scope（密码哈希）
data/state/points.json       # 点位：device_id、账号、最近在线、状态
data/state/sessions.json     # refresh_token → 账号/点位/到期
data/logs/auth.log           # 登录、吊销、越权、上传审计
```

## 九、迁移步骤

1. 服务端加账号与签名令牌（不动现有表与计划格式）。
2. 给学生211建第一个 floor 账号（B 座一层），发一次性初始密码。
3. iPad 端加登录页与名册缓存；旧版自动当 B 座一层。
4. 跑一周无异常后，给二层、三层各建账号，旧 token 收回。
5. 女生楼账号同法接入。

## 十、不做什么

- 不做学生/家长账号（家长只看链接）。
- 不做 SSO、不做扫码登录、不做人脸登录。
- 不在客户端存密码，只存可吊销的 refresh_token。
- 不做跨层代点（防止一层老师替别层签到，留不下本人痕迹）。

## 十二、一句话

**账号决定层，设备决定谁能用这台 iPad，服务端只信账号不信参数。** 七台 iPad 各登各的账号，看见的自然是各自那层，写回的自然也落各自那层。
